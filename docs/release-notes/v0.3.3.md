### What changed

**A batched request no longer walks past the gateway.** JSON-RPC lets a client
send several messages as one line, a top-level array instead of an object.
Ganimedes' request parser expects one message per line, so a batch failed to
parse and fell through to the branch that forwards anything it cannot read.
A `tools/call` inside that array therefore reached the wrapped server with no
policy check and no audit entry — deny-list configured, approval-list
configured, both bypassed, by nothing cleverer than a pair of brackets.

This was reachable, not theoretical. Batching is legal on the wire under MCP
protocol versions `2024-11-05` and `2025-03-26`; it was removed from the spec
only in `2025-06-18`, and `run` negotiates no protocol version of its own,
because it proxies bytes between a client and a server that negotiate with each
other. Any pair of them still speaking an older version could send one.

A batch is now refused whole. Deciding its elements one by one would mean
building batch semantics — split, judge each, re-encode the survivors,
recombine the responses — for a wire form the spec itself has retired, on a
proxy that otherwise never re-encodes what it forwards. Every id in the batch
gets its own JSON-RPC error back, in an array shaped like the batch, so a
client can still correlate the refusal, and the raw batch is recorded verbatim
in the audit log so you can see exactly what was attempted. **If you have a
client that genuinely sends batches, this is the one behavior change you will
notice: those calls now come back as errors instead of silently going through.**

**A reused request id no longer corrupts the record.** Ganimedes pairs a
`tools/call` with its response by JSON-RPC id. Two calls sharing one id, while
the first was still waiting, used to leave only the second one remembered:
whichever response came back first was logged under the wrong tool name, and
the other call finished with no audit entry at all. No policy was bypassed
there — every request is still judged on its own — but "prove what your agent
did" is exactly the claim that weakens, so it is treated as the same class of
problem.

The wire gives no way to tell which of two responses to one id belongs to which
request, so the second call is refused rather than guessed at. A call a human
approved is refused too if its id collided while they were deciding: the
approval is about the call, not about whether the record of it can be trusted.
The cost, stated rather than left to be found: a call the server never answers
holds its id for the rest of the session, and a later call reusing that id is
refused as well. There is no expiry, because a timeout short enough to release
a stuck id is also short enough to release one whose response is merely slow,
which would put the misattribution back. Every MCP client counts ids upward and
never revisits one, so in practice this costs nothing.

**How this was found.** The same exercise that produced `v0.3.2`, continued:
reading the code against `SECURITY.md`'s own list of what counts as in scope,
rather than against what the docs claim is already handled. The line that
matched here was "a way to make the gateway forward without a decision", and
the batch was precisely that. Both fixes were then checked against a deliberate
break of the code they cover, to confirm the new tests are able to fail.

Patch rather than minor: no flag, exit code, config key or log format changed,
and logs written by earlier versions still verify. **Upgrade ahead of `v0.3.2`
if you rely on the deny-list or on approvals at all** — the batch gap did not
require approvals to be configured, so it reached further than the page
vulnerability `v0.3.2` closed.
